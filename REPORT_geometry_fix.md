### 1. Причина расхождения геометрии — waypoints (коммиты `9d4b792`, `eb38e00`)

**Модель** (`src/pdf_to_ifc/model.py`):

- `NetworkEdge.waypoints: List[Tuple[float, float, float]] = []` — точки изгиба
  между `start_node` и `end_node` по порядку. Пустой список = прежнее поведение.
- `__post_init__` нормализует точки к кортежам `float` (после JSON-раунд-трипа
  они приходят списками — без нормализации `to_dict()` до и после сериализации
  давали бы разные структуры).
- `polyline()`, `polyline_length()`, `length_mismatch()` — геометрия трассы и её
  расхождение со спецификацией. Модель намеренно **не** синхронизирует `length`
  с длиной ломаной: какая величина главнее — решает инженер.
- `calculate_slope()` по-прежнему считает по `length`: уклон — свойство трубы,
  а не точности её оцифровки.
- В докстринге модуля явно описано расхождение с контрактом с доски Miro
  (`branch`, расширенный `node_type`, `waypoints`) — это задача 2 брифа.

**Экспорт** (`src/pdf_to_ifc/ifc_export.py`):

- `_create_edge_products()` разворачивает ребро в ломаную и создаёт по
  `IfcPipeSegment` на каждое звено; `Depth` = фактическое расстояние между
  концами звена, а не `edge.length` целиком на каждое звено.
- В каждой промежуточной точке — `IfcPipeFitting` с `PredefinedType="BEND"`.
  В узлах сети фитинги не ставятся: там уже есть объекты узлов из задачи 7.
- Под-сегменты именуются `A->B (branch) [i/n]`.
- Пустой `waypoints` даёт ровно прежний результат: одна труба, прежнее имя,
  `Depth = edge.length`. Почему для прямого участка сохранена именно
  спецификационная длина — расписано в докстринге модуля (пока трасса не
  оцифрована, это единственный источник длины трубы, и подменять её прямым
  расстоянием значило бы молча терять данные спецификации).

**Попутный баг (не из брифа).** `_perpendicular_direction()` выбирал опорный
вектор `(1, 0, 0)` ровно тогда, когда ось трубы почти совпадает с X, — проекция
вырождалась в ноль, и экспорт падал с «Нулевая длина направления трубы» на
горизонтальной трубе вдоль оси X. Теперь опорной берётся ось с наименьшей по
модулю компонентой. Тестовый датасет промахивался мимо этого случая на 2·10⁻⁶
(шаг 50 м при перепаде отметок 0.1 м), поэтому баг не был виден.

### 2. Типы узлов из эталона (коммит `68e28fd`)

По решению человека модель расширена под то, что реально есть в эталоне:
`valve` → `IfcValve`, `casing` → `IfcPipeFitting`, `channel` →
`IfcDistributionChamberElement`, `connection_point` → `IfcDistributionPort`
с `PredefinedType="PIPE"` (у порта это тип переносимой среды, а не «тип
объекта»). Порт не кладётся в пространственную структуру — по схеме он не
элемент. Эталонные `IfcBuildingElementProxy` мы не копируем: генерируем
осмысленные классы, а сверяемся по геометрии.

### 3. Задача 9 — свойства труб (коммит `f769690`)

На каждый `IfcPipeSegment` — набор `Pset_PdfToIfc_PipeSegment`: `DN` (мм),
`Material`, `Insulation`, `LayingType`, `Branch`, `Slope`, `SpecLength`,
`SegmentLength`, `SegmentIndex`, `SegmentCount`, `SourceEdge`.

Давление и температура **не пишутся**: их нет ни в доменной модели, ни в
датасете (извлечение из PDF — задачи 12-20). Пустое свойство в вьюере выглядит
как заполненное, поэтому свойства просто нет, а причина зафиксирована TODO
в коде. Там же TODO про обозначение трубы по ГОСТ — в эталоне оно есть

### 5. Задача 5 брифа — `scripts/validate_geometry.py` (коммиты `264cc13`, `7f35076`)

Сравнение по IFC-классам невозможно: эталон в IFC2X3 (нет `IfcPipeSegment`
вовсе), геометрия эталона — `IfcFacetedBrep`, наша — `IfcExtrudedAreaSolid`.
Поэтому через `ifcopenshell.geom` из обоих файлов извлекаются вершины тел в
мировых координатах, из облака вершин каждого тела восстанавливается осевая
линия (первая главная компонента SVD = ось, концы — крайние проекции вершин),
и сравниваются осевые линии, полученные **одинаковым способом** с обеих сторон.

- Фильтр систем: Т1/Т2/Т1/Т2 (130 труб из 165), дренаж «Др» (35) отбрасывается.
- Метрика: осевая линия дискретизируется на N точек, для каждой считается
  расстояние до ближайшей точки эталонной сети (точка-отрезок, векторно на
  numpy). Отклонение участка = максимум по точкам. Считаются оба направления.
- `scipy.directed_hausdorff` не используется намеренно: он меряет расстояние
  между наборами точек, а нам нужно до непрерывных отрезков, иначе результат
  зависел бы от частоты дискретизации эталона.
- Допуск: `min(0.2 м, 5 % длины участка)`.
- Выравнивание координат по умолчанию не делается; `--align centroid` —
  диагностика формы, в отчёте подписана как «не приёмка».
- `--json` сохраняет машиночитаемый отчёт; код возврата 1, если не вся длина
  сети в допуске (чтобы скрипт можно было ставить в CI).

## Расследование: откуда взялось расхождение по диаметрам

Первая версия сводки показывала DN 325 −24.5 % и DN 426 **+135.0 %** при
сходящейся суммарной длине. Смещением систем координат и разницей формы
трассы это не объясняется — длины от координат не зависят вовсе. Разбор дал
**две независимые причины**: одна в скрипте сверки, вторая в данных.

### Причина 1 — ошибка в `validate_geometry.py` (исправлена)

DN трубы в эталоне лежит в двух местах:

- свойство **«Диаметр»** набора «Труба» — число в метрах;
- свойство **«Наименование»** — обозначение по ГОСТ вида
  `Ст 426х9,0/560 ППУ-ПЭ в изоляции по ГОСТ 30732-2020`, где 426 — наружный
  диаметр стальной трубы в мм, 9,0 — толщина стенки, 560 — оболочка ППУ.

Сводка читала только «Диаметр». А у **18 из 130** труб систем Т1/Т2 это
свойство пустое — при том что обозначение у них заполнено, и все 18 по нему
`Ст 426х9,0/560`. Эти 214.17 м уходили в строку «не указан», то есть длина
эталона по DN 426 занижалась почти вдвое:

| | было | стало |
|---|---|---|
| DN 426 в эталоне | 255.32 м | 469.49 м (188.25 ППУ-ОЦ + 67.07 ППУ-ПЭ + 214.17 без «Диаметра») |
| расхождение с нашим файлом | +135.0 % | **+27.8 %** |
| строка «не указан» | 214.17 м | нет, DN известен у всех 130 труб |

Исправлено: `_reference_dn()` разбирает обозначение по ГОСТ как запасной
источник. Приоритет остаётся у «Диаметра» — это явное числовое поле, а
обозначение заполняет человек. Восстанавливать DN по толщине BREP-тела
по-прежнему нельзя: тело эталона построено по наружному диаметру оболочки
(560 мм при DN 426), такая подмена тихо исказила бы сводку.

Регресс-тесты: 6 штук, из них 4 падают на коде до фикса (два оставшихся
фиксируют поведение, которое не менялось — приоритет «Диаметра» и `None`,
когда диаметра нет нигде).

### Причина 2 — данные датасета (НЕ исправлял, открытый вопрос)

Оставшиеся +27.8 % / −24.5 % — не баг скрипта. В `data/samples/parnas_edges.csv`
все 24 ребра имеют `length = 50`, то есть длина участка — такой же
синтетический placeholder, как и координаты X/Y (шаг 50 м из задачи 4), а не
величина из спецификации. Разбиение по диаметрам получается ровно пополам,
12 участков на 12: DN 426 — от УТ-1 до УК2, DN 325 — от УК2 до ТК-4.

В эталоне пропорция другая: 469.49 м против 795.02 м, то есть переход
Ф426 → Ф325 приходится примерно на 37 % длины трассы, а не на 50 %. При
средней длине эталонного участка ~9.7 м это означает, что в датасете переход
поставлен на 2–3 узла позже реального.

Важно: это НЕ значит, что в датасете ошибка в спецификации. Значит только,
что при длинах-placeholder'ах сводка по DN меряет не спецификацию, а
искусственный шаг 50 м. Пока `length` не придёт из распарсенной спецификации
(задачи 12–16), сравнивать по DN имеет смысл только структуру («два диаметра,
один переход»), а не километры. `data/samples` я не трогал — бриф запрещает
менять существующие файлы датасета без явного указания.

## Решения, принятые человеком (не мной)

1. **Объём работ**: пункты 1, 3, 5, 7 брифа + отчёт + разведка PDF (Ш0).
   Задачи 12-20 (полноценный парсинг PDF) в этот прогон не входят.
2. **Типы узлов**: расширить модель сейчас (арматура, футляр, канал, точка
   подключения) — вариант «оставить вне скоупа» отклонён.
3. **Порог допуска**: 0.2 м по дорожной карте вместо чернового 0.3 м из брифа,
   чтобы в проекте не жило два разных порога на одно и то же.
4. **Коммиты**: ветка `geometry-fix`, пуш в неё, без прямого пуша в `main`.

## Открытые вопросы

Ни один из них не решён в коде — все требуют человека.

1. **Система координат PDF-плана относительно эталона.** Подписей
   координатной сетки в тексте PDF нет (текст на планах в кривых), слоёв OCG
   нет. Значит, привязка не выводится из файла автоматически. Варианты:
   взять её из DWG (в дорожной карте DWG назван эталоном, но в репозитории
   его нет), запросить у проектировщика, или ставить вручную по двум опорным
   точкам в редакторе (Ш5). До этого `validate_geometry.py` будет показывать
   расхождение из-за смещения систем координат.
2. **Порог допуска 0.2 м — подтвердить на реальных данных.** Сейчас он взят
   из дорожной карты и ни разу не проверялся на данных, где сравнение вообще
   осмысленно (координаты в одной системе). Может оказаться и слишком грубым,
   и слишком строгим. Скрипт порог сам не подбирает и не будет.
3. **Подача и обратка у нас геометрически совпадают.** В доменной модели
   координата одна на узел, поэтому нитки `supply` и `return` лежат в одной
   линии. В эталоне Т1 и Т2 — физически разные трубы: измеренное расстояние
   между ними медиана **0.70 м** (от 0.40 до 0.81 м). Это больше допуска
   0.2 м, то есть даже при идеально оцифрованных координатах одна из двух

   тогда откуда брать смещение — из типового узла прокладки?) или считать
   допустимым и сверять по осевой линии участка, а не по каждой нитке.
4. **Где на самом деле стоит переход Ф426 → Ф325.** После исправления

## Что осталось за рамками

- Задачи 12-20 (парсинг спецификации, профиля, координат плана) — по решению
  человека не входили в этот прогон. Ш0 к ним сделан, и он меняет их оценку:

  Правка оказалась не в генераторе, а в самом инструменте сверки (добавлена
  метрика, не зависящая от системы координат), потому что на текущих данных
  отклонение геометрии объясняется целиком смещением систем координат, и
  «чинить» по нему генератор означало бы подгонять код под артефакт данных.
  Дальнейшие круги имеют смысл после решения открытого вопроса 1.
- Задача 3 (`validate()`) не трогалась — она отложена в `BACKLOG.md`, и бриф
  прямо требует не реализовывать её по устаревшему описанию с доски Miro.
