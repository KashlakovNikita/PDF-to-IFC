### 1. Причина расхождения геометрии — waypoints (коммиты `9d4b792`, `eb38e00`)

**Модель** (`src/pdf_to_ifc/model.py`):

- `NetworkEdge.waypoints: List[Tuple[float, float, float]] = []` — точки изгиба
  между `start_node` и `end_node` по порядку. Пустой список = прежнее поведение.
- `__post_init__` нормализует точки к кортежам `float` (после JSON-раунд-трипа
  они приходят списками — без нормализации `to_dict()` до и после сериализации
  давали бы разные структуры).
- `polyline()`, `polyline_length()`, `length_mismatch()` — геометрия трассы и её
  расхождение со спецификацией. Модель намеренно **не** синхронизирует `length`
  с длиной ломаной: какая величина главнее — решает инженер.
- `calculate_slope()` по-прежнему считает по `length`: уклон — свойство трубы,
  а не точности её оцифровки.
- В докстринге модуля явно описано расхождение с контрактом с доски Miro
  (`branch`, расширенный `node_type`, `waypoints`) — это задача 2 брифа.

**Экспорт** (`src/pdf_to_ifc/ifc_export.py`):

- `_create_edge_products()` разворачивает ребро в ломаную и создаёт по
  `IfcPipeSegment` на каждое звено; `Depth` = фактическое расстояние между
  концами звена, а не `edge.length` целиком на каждое звено.
- В каждой промежуточной точке — `IfcPipeFitting` с `PredefinedType="BEND"`.
  В узлах сети фитинги не ставятся: там уже есть объекты узлов из задачи 7.
- Под-сегменты именуются `A->B (branch) [i/n]`.
- Пустой `waypoints` даёт ровно прежний результат: одна труба, прежнее имя,
  `Depth = edge.length`. Почему для прямого участка сохранена именно
  спецификационная длина — расписано в докстринге модуля (пока трасса не
  оцифрована, это единственный источник длины трубы, и подменять её прямым
  расстоянием значило бы молча терять данные спецификации).

**Попутный баг (не из брифа).** `_perpendicular_direction()` выбирал опорный
вектор `(1, 0, 0)` ровно тогда, когда ось трубы почти совпадает с X, — проекция
вырождалась в ноль, и экспорт падал с «Нулевая длина направления трубы» на
горизонтальной трубе вдоль оси X. Теперь опорной берётся ось с наименьшей по
модулю компонентой. Тестовый датасет промахивался мимо этого случая на 2·10⁻⁶
(шаг 50 м при перепаде отметок 0.1 м), поэтому баг не был виден.

### 2. Типы узлов из эталона (коммит `68e28fd`)

По решению человека модель расширена под то, что реально есть в эталоне:
`valve` → `IfcValve`, `casing` → `IfcPipeFitting`, `channel` →
`IfcDistributionChamberElement`, `connection_point` → `IfcDistributionPort`
с `PredefinedType="PIPE"` (у порта это тип переносимой среды, а не «тип
объекта»). Порт не кладётся в пространственную структуру — по схеме он не
элемент. Эталонные `IfcBuildingElementProxy` мы не копируем: генерируем
осмысленные классы, а сверяемся по геометрии.

### 3. Задача 9 — свойства труб (коммит `f769690`)

На каждый `IfcPipeSegment` — набор `Pset_PdfToIfc_PipeSegment`: `DN` (мм),
`Material`, `Insulation`, `LayingType`, `Branch`, `Slope`, `SpecLength`,
`SegmentLength`, `SegmentIndex`, `SegmentCount`, `SourceEdge`.

Давление и температура **не пишутся**: их нет ни в доменной модели, ни в
датасете (извлечение из PDF — задачи 12-20). Пустое свойство в вьюере выглядит
как заполненное, поэтому свойства просто нет, а причина зафиксирована TODO

### 5. Задача 5 брифа — `scripts/validate_geometry.py` (коммиты `264cc13`, `7f35076`)

Сравнение по IFC-классам невозможно: эталон в IFC2X3 (нет `IfcPipeSegment`
вовсе), геометрия эталона — `IfcFacetedBrep`, наша — `IfcExtrudedAreaSolid`.
Поэтому через `ifcopenshell.geom` из обоих файлов извлекаются вершины тел в
мировых координатах, из облака вершин каждого тела восстанавливается осевая
линия (первая главная компонента SVD = ось, концы — крайние проекции вершин),
и сравниваются осевые линии, полученные **одинаковым способом** с обеих сторон.

- Фильтр систем: Т1/Т2/Т1/Т2 (130 труб из 165), дренаж «Др» (35) отбрасывается.
- Метрика: осевая линия дискретизируется на N точек, для каждой считается
  расстояние до ближайшей точки эталонной сети (точка-отрезок, векторно на
  numpy). Отклонение участка = максимум по точкам. Считаются оба направления.
- `scipy.directed_hausdorff` не используется намеренно: он меряет расстояние
  между наборами точек, а нам нужно до непрерывных отрезков, иначе результат
  зависел бы от частоты дискретизации эталона.
- Допуск: `min(0.2 м, 5 % длины участка)`.
- Выравнивание координат по умолчанию не делается; `--align centroid` —
  диагностика формы, в отчёте подписана как «не приёмка».
- `--json` сохраняет машиночитаемый отчёт; код возврата 1, если не вся длина
  сети в допуске (чтобы скрипт можно было ставить в CI).

## Расследование: откуда взялось расхождение по диаметрам

Первая версия сводки показывала DN 325 −24.5 % и DN 426 **+135.0 %** при
сходящейся суммарной длине. Смещением систем координат и разницей формы
трассы это не объясняется — длины от координат не зависят вовсе. Разбор дал
**две независимые причины**: одна в скрипте сверки, вторая в данных.

### Причина 1 — ошибка в `validate_geometry.py` (исправлена)

DN трубы в эталоне лежит в двух местах:

- свойство **«Диаметр»** набора «Труба» — число в метрах;
- свойство **«Наименование»** — обозначение по ГОСТ вида
  `Ст 426х9,0/560 ППУ-ПЭ в изоляции по ГОСТ 30732-2020`, где 426 — наружный
  диаметр стальной трубы в мм, 9,0 — толщина стенки, 560 — оболочка ППУ.

Сводка читала только «Диаметр». А у **18 из 130** труб систем Т1/Т2 это
свойство пустое — при том что обозначение у них заполнено, и все 18 по нему
`Ст 426х9,0/560`. Эти 214.17 м уходили в строку «не указан», то есть длина
эталона по DN 426 занижалась почти вдвое:

| | было | стало |
|---|---|---|
| DN 426 в эталоне | 255.32 м | 469.49 м (188.25 ППУ-ОЦ + 67.07 ППУ-ПЭ + 214.17 без «Диаметра») |
| расхождение с нашим файлом | +135.0 % | **+27.8 %** |
| строка «не указан» | 214.17 м | нет, DN известен у всех 130 труб |

Исправлено: `_reference_dn()` разбирает обозначение по ГОСТ как запасной
источник. Приоритет остаётся у «Диаметра» — это явное числовое поле, а
обозначение заполняет человек. Восстанавливать DN по толщине BREP-тела
по-прежнему нельзя: тело эталона построено по наружному диаметру оболочки
(560 мм при DN 426), такая подмена тихо исказила бы сводку.

Регресс-тесты: 6 штук, из них 4 падают на коде до фикса (два оставшихся
фиксируют поведение, которое не менялось — приоритет «Диаметра» и `None`,
когда диаметра нет нигде).

### Причина 2 — данные датасета (НЕ исправлял, открытый вопрос)

Оставшиеся +27.8 % / −24.5 % — не баг скрипта. В `data/samples/parnas_edges.csv`
все 24 ребра имеют `length = 50`, то есть длина участка — такой же
синтетический placeholder, как и координаты X/Y (шаг 50 м из задачи 4), а не
величина из спецификации. Разбиение по диаметрам получается ровно пополам,
12 участков на 12: DN 426 — от УТ-1 до УК2, DN 325 — от УК2 до ТК-4.

В эталоне пропорция другая: 469.49 м против 795.02 м, то есть переход
Ф426 → Ф325 приходится примерно на 37 % длины трассы, а не на 50 %. При
средней длине эталонного участка ~9.7 м это означает, что в датасете переход
поставлен на 2–3 узла позже реального.

Важно: это НЕ значит, что в датасете ошибка в спецификации. Значит только,
что при длинах-placeholder'ах сводка по DN меряет не спецификацию, а
искусственный шаг 50 м. Пока `length` не придёт из распарсенной спецификации
(задачи 12–16), сравнивать по DN имеет смысл только структуру («два диаметра,
один переход»), а не километры. `data/samples` я не трогал — бриф запрещает
менять существующие файлы датасета без явного указания.

## Задача 31: реальные координаты из DWG — и что они показали

Заказчик передал исходные DWG (`data/reference/dwg`, 5 файлов, AC1024). Они
сконвертированы в DXF через ODA File Converter 27.1.0 и разобраны через `ezdxf`
(`scripts/extract_from_dwg.py`). Выгрузка легла в `data/derived/parnas_dwg_*`;
`data/samples` не менялся.

### Открытый вопрос 1 закрыт: система координат та же

Плановые координаты DWG — X 115751..117130, Y 108074..110563. Это ровно та же
местная система, что и в эталонном IFC (X ~116300, Y ~110430), оси не
переставлены. Никакой привязки не требуется, координаты сравнимы напрямую.

Слой оси выбран измерением, а не по названию: осевые линии эталона легли на
`_ПР_Теплосеть` со 100 % точек ближе 1 м, на топооснову `32_Теплосеть` — с
медианой 0.14 м, а на похожий по имени `_ПР_Теплосеть_1_ВТС` — с медианой
7.86 м, то есть это вообще другая линия. Подтверждение: 33 марки узлов из 35
указывают на выбранную ось с расстоянием 0.00 м.

| максимум того же направления | 160 393.574 м | 2.206 м | **2.195 м** |

| длина сети (обе нитки) | 1200.00 м | 1403.98 м | 1403.98 м (эталон 1266.52 м) |

Расхождение упало в 274 тысячи раз относительно синтетических координат. В
допуск 0.2 м по-прежнему не попадает ничего: у двух ниток одна геометрическая
ось, а модель покрывает только часть эталонной сети.

### Находка 1 закрыта задачей 32: ось трубы поднята над лотком

До исправления медиана 3D-отклонения была 0.667 м при медиане Z эталона
26.18 м и нашей 25.93 м: сеть систематически лежала ниже примерно на 0.25 м.

Причина была в генераторе: `generate_ifc_from_network()` ставил ось трубы в
`z_pipe_bottom` — отметку **лотка**. В задаче 32 начало каждого
`IfcPipeSegment` и каждый отвод поднимаются на `edge.diameter / 2000` м;
узлы сети остаются на своей исходной отметке. После пересборки DWG-модели
медиана отклонения уменьшилась на 0.083 м: с 0.667 до 0.584 м.

Правило использует DN, а не наружный диаметр ППУ-оболочки. Если профиль задаёт
лоток именно по изоляции, результат будет ниже оси оболочки; это ограничение
данных, но не повод оставлять ось трубы на отметке лотка.

### Находка 2: 0.2 м недостижимы, пока обе нитки лежат на одной оси

Оставшиеся 0.51 м по XY — это примерно половина разноса ниток: в эталоне Т1 и
Т2 разведены на 0.70 м (медиана, диапазон 0.40..0.81), а мы кладём подачу и
обратку на одну осевую линию. Половина разноса — 0.35 м — уже больше допуска
0.2 м сама по себе, безотносительно качества оцифровки.

Отсюда прямой вывод про порог: **0.2 м сейчас недостижимы по построению, а не
из-за ошибок геометрии.** Порог менять не надо — надо разнести нитки (задача 26)
и починить отметку оси (находка 1); до этого сверка меряет не точность
оцифровки, а два известных систематических смещения. Оба измерены, оба
устранимы.

### Задача 33: обычный TEXT/MTEXT возле профиля — не найдено

сущности (196 `TEXT`, 188 `MTEXT`) с координатами. Числовых отметок в диапазоне

же пять отметок, которые уже учитывались; дополнительной копии значений рядом

В остальных DXF есть числа в разрезах камер (`07_*ТК.dxf`) и одна отметка в

связаны с марками узлов и станциями профиля. Безопасно перенести их в сетевую
модель невозможно. Основные значения по-прежнему лежат в атрибутах `LEVEL`:

динамические поля AutoCAD после конвертации в DXF не материализовались.

Итог ограниченной проверки: **не найдено, нужен ручной ввод**. Z для известных
узлов остаётся из `data/samples/parnas_nodes.csv`; для 20 остальных узлов
следует вводить отметки через `manual_input`. Калибровка профиля по
вертикальному масштабу — отдельная задача с ручной сверкой.

## Задача 26: разнос ниток — измерено, а не предположено

Вопрос стоял так: различает ли чертёж подачу и обратку геометрически. Проверено
тем же способом, каким раньше выбирался слой оси, — сравнением с эталоном по
расстоянию, а не по названию слоя.

### В плане двух контуров нет

| Что проверено | Результат |
|---|---|
| Проектный слой `_ПР_Теплосеть` | Все **31** отрезков, идущих параллельно трассе, лежат на НУЛЕВОМ отступе от неё — одна осевая линия |
| Эталонные Т1 и Т2 относительно этой оси | Стоят симметрично по **0.35 м** в каждую сторону (Т1 преимущественно слева, Т2 справа) — ось проходит ровно между ними |
| Топооснова `32_Теплосеть` | Параллельные отрезки размазаны от −1.5 до +1.5 м без двух чётких пиков; к тому же это существующая сеть до реконструкции |
| MLINE на слоях теплосети | Рисует две линии на 1.28 / 1.64 / 1.74 м — это **стенки канала** (совпадает с шириной «Канала» в эталоне), а не нитки |

### Но в сечениях расстояние есть

На листе «л.4 Сечения» нитки подписаны раздельно — «Т1 Ø426х9,0» и
«Т2 Ø426х9,0», каждая со своей окружностью. Лист начерчен в миллиметрах
(радиусы 162.5 и 213.0 при Ду 325 и Ду 426), поэтому расстояние между осями
читается прямо оттуда:

- **Ду 325 — 700 мм**, 11 пар подписей;
- **Ду 426 — 800 мм**.

Это данные чертежа, а не подобранное число. Совпадение с эталоном (медиана
разноса Т1↔Т2 = 0.70 м, диапазон 0.40..0.81) — независимое подтверждение, а не
источник: числа взяты до того, как сверялись с эталоном.

Чего в данных нет: КАКАЯ нитка идёт слева, а какая справа. В сечении порядок
есть, но перенести его на план можно, только разобрав направление взгляда
разрезов. Поэтому `--separate-threads` по умолчанию **выключен**, а сторона
в коде — явно помеченное допущение, а не измерение.

### Что дал разнос (ответ на вопрос про XY)

Первая же цифра оказалась обманчивой, и это стоит знать: по основной метрике
(максимум отклонения на участок) разнос почти ничего не изменил, XY-медиана
сдвинулась с 0.510 лишь до 0.500 м. Похоже было, что гипотеза не подтвердилась.

На самом деле метрика прятала эффект. Если смотреть распределение по ВСЕМ
точкам, а не по максимуму на участок:

| | медиана XY по точкам | точек в пределах 0.2 м |
|---|---|---|
| одна общая ось (как было) | 0.350 м | **0.9 %** |
| нитки разведены по сечениям | **0.002 м** | **82.6 %** |

То есть разнос ниток был почти всей XY-ошибкой: типичное отклонение упало с
35 см до 2 мм, и 0.350 м — это ровно половина паспортных 0.70 м, как и должно
быть при обеих нитках на одной оси.

Медиана максимумов по участкам осталась около 0.5 м из-за оставшихся 17 %
точек (p95 ≈ 1.2 м) — это места, где наша трасса действительно отличается от
эталонной: прямые вставки там, где в чертеже разрыв линии, и участок Н7→УК6 с
отклонением 2.4 м. Это уже не про нитки.

Обе метрики теперь печатает сам `validate_geometry.py`: максимум по участку —
для приёмки (участок с одним плохим местом не должен считаться хорошим), и
распределение по точкам — чтобы такие эффекты не терялись. Расхождение между
ними не ошибка, а разные вопросы к одним данным.

### Итог по задаче 26

Раздельные графы (сделаны раньше) теперь наполнены данными: расстояние между
нитками берётся из сечений, по диаметру участка. Включение разноса — одно
решение человека:

```
python scripts/extract_from_dwg.py --separate-threads
```

С ним геометрия сети становится верной с точностью до миллиметров; без него
остаётся систематические 0.35 м. Не включено по умолчанию только из-за
неопределённой стороны: если окажется, что supply на самом деле идёт справа,
поменяются местами подписи ниток, но не геометрия сети.

## Задача 33: поиск отметок в DXF

Про задачу 32 (подъём оси над лотком) всё сказано выше, в разделе про DWG.
Здесь — одно уточнение к её остатку и результаты поиска отметок.

**Остаток −0.087 м по Z не случаен.** Подъём считается по DN (радиус 0.213 м
для Ст426), а наружный диаметр ППУ-оболочки больше — 0.28 м при 560 мм.
Разница 0.067 м того же порядка, что и остаток: похоже, в эталоне отметка
отсчитывается по изоляции, а не по стальной трубе (открытый вопрос 10).

### Земля найдена, лоток нет

Проверены все пять чертежей целиком: пространство модели, листы (paper space),
определения блоков, атрибуты вхождений, тексты размеров и выносок.

**Отметки земли — нашлись и взяты в работу.** На плане есть слой
«61_Отметки высоты поверхности»: 611 съёмочных подписей, 146 из них ближе 5 м к
трассе. Экстрактор берёт ближайшую подпись к узлу (радиус настраивается флагом
`--ground-radius`). Результат: **12 узлов из 13** получили отметку земли прямо с
чертежа, медиана расхождения с отметками, снятыми человеком, — **0.04 м**,
максимум 0.35 м. Два независимых источника сошлись.

**Отметки лотка — не нашлись.** Что есть и почему не подходит:

| Где | Что там | Почему не годится |
|---|---|---|
| Профиль, атрибуты `LEVEL` | 109 вхождений | Динамические поля AutoCAD: в определении блока заглушка `"0.000"`, в экземплярах пусто. В DXF не материализуются |
| Профиль, текст | 5 отметок из нескольких сотен | Выписаны единично, к узлам не привязаны |
| План, слой «32_Теплосеть» | 48 подписей (26.4…29.1) | Это **существующая** сеть, топооснова. Систематически на 0.4…1.1 м выше нашего лотка — верх или ось существующих труб |
| Лист ТК, слой «Pipe» | 30 подписей | Лист собран в собственных координатах узлов, связать с планом автоматически не на чем |
| Профиль, блок «шкала» | 25,00 / 26,00 / 27,00 | Вертикальная шкала листа. Через неё отметки восстановимы калибровкой, но это отдельная задача |

**Вывод: отметки лотка вводятся руками** (`pdf_to_ifc.manual_input`) либо
восстанавливаются калибровкой профиля по вертикальному масштабу (Мв 1:100).
Второе — самостоятельная задача со сверкой по бумаге, а не побочный эффект
этой: цифра иначе получится правдоподобной и непроверяемой. Поиск остановлен
намеренно, дальше он не окупается.

## Что осталось за рамками

- Задачи 12-20 (парсинг спецификации, профиля, координат плана) — по решению
  человека не входили в этот прогон. Ш0 к ним сделан, и он меняет их оценку:

  отклонение геометрии объясняется целиком смещением систем координат, и
  «чинить» по нему генератор означало бы подгонять код под артефакт данных.
  Дальнейшие круги имеют смысл после решения открытого вопроса 1.
- Задача 3 (`validate()`) не трогалась — она отложена в `BACKLOG.md`, и бриф
  прямо требует не реализовывать её по устаревшему описанию с доски Miro.
