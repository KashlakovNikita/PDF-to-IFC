# PDF/DWG → IFC: цель, результат, шаги

Версия 1 · 2026-09-03 · дополняет `pdf_to_ifc_analysis.md` (кода здесь нет намеренно)

Вводные, от которых пляшем:

- **Инструмент, а не разовая конвертация.** Работает на инженерных сетях вообще (ТС, ВК, К, ГС), потому что принципы построения сетей одинаковы.
- **Human-in-the-loop.** Парсер даёт черновик, инженер правит в редакторе, экспорт по кнопке.
- **Приёмка по геометрии и объектам:** 3D-трассы с реальными XYZ и Ду + камеры, арматура, опоры.
- **Исходник векторный, печать из AutoCAD; есть DWG.**

---

## 1. Что мы строим

Приложение с тремя экранами и одним ядром:

```
   ┌── Импорт ────────┐   ┌── Проверка/правка ─────────┐   ┌── Экспорт ──────┐
   │ PDF (вектор)     │   │ План на подложке чертежа   │   │ IFC 4.3         │
   │ DWG              │──▶│ Таблица участков и узлов   │──▶│ + отчёт сверки  │
   │ (растр — позже)  │   │ Профиль с отметками        │   │ + DXF для сверки│
   └──────────────────┘   └────────────────────────────┘   └─────────────────┘
                                       ▲  ▼
                          ┌────────────────────────────┐
                          │  Нейтральная модель сети   │  ← единственный источник правды
                          │  граф + атрибуты +         │
                          │  происхождение + доверие   │
                          └────────────────────────────┘
```

Ключевая идея: **парсер, редактор и генератор IFC не знают друг о друге**. Они общаются только через нейтральную модель. Это то, что делает инструмент переносимым на другие типы сетей и на другие форматы источника — меняется только экстрактор и словарь.

---

## 2. Как выглядит «готово»

Критерии приёмки, по которым можно спорить с фактами, а не с ощущениями.

**Файл**

- IFC 4.3 (IFC4X3_ADD2), проходит `ifcopenshell.validate` без ошибок схемы.
- Открывается в Revit, Navisworks и BlenderBIM без предупреждений о геометрии.
- Георефернс: локальная СК модели + `IfcMapConversion` → МСК (не пишем координаты вида 116763.09 напрямую в вершины: теряется точность и часть вьюеров ломается).

**Содержание**

| Объект на чертеже | В модели |
|---|---|
| Участок трубопровода | `IfcPipeSegment` + `IfcSweptDiskSolid` по осевой (наружный Ø стали; оболочка ППУ — вторым телом или как Pset) |
| Поворот, тройник, переход | `IfcPipeFitting` (BEND / JUNCTION / TRANSITION) |
| Тепловая камера ТК, узел УТ | `IfcDistributionChamberElement` (VALVECHAMBER / MANHOLE) с габаритом и отметками |
| Кран, задвижка | `IfcValve` в разрыве трассы |
| Неподвижная / скользящая опора | `IfcDiscreteAccessory` в точке на трассе |
| Сильфонный компенсатор | `IfcPipeFitting` + классификация (в схеме нет отдельной сущности) |
| Сеть целиком | `IfcDistributionSystem` (PredefinedType=HEATING), подача и обратка — раздельные системы |

**Точность**

- Плановое положение осей: расхождение с исходным чертежом ≤ **0.2 м** при наложении (обратный экспорт в DXF поверх исходника).
- Отметки лотка в узлах: ≤ **0.05 м** от значений профиля.
- Суммы длин по каждому Ду: расхождение с ведомостью объёмов ≤ **3 %**, каждое расхождение объяснено в отчёте.
- Все элементы имеют Ду, материал, тип прокладки; ни одного с `confidence = auto, unconfirmed` на выходе.

**Процесс**

- Проект уровня Парнаса (≈400 элементов, ≈30 узлов) от загрузки до экспорта — **не больше рабочего дня** одного инженера, из них машинного времени минуты.

## 3. Четыре поправки к текущему анализу

Прежде чем расписывать шаги — что я бы поменял в `pdf_to_ifc_analysis.md`.

**3.1. ML-классификатор диаметров — убрать из плана.**
В документе диаметр участка предсказывается LightGBM по соседям и топологии. Это решение задачи, которой нет: диаметры на чертеже подписаны выносками («Ст 325×8,0»), продублированы в спецификации и в ведомости по типам прокладки. Нужен детерминированный маппинг «выноска → участок» плюс сверка сумм, а не вероятностная модель, обученная неизвестно на чём. ML оставляем ровно в одном месте — распознавание условных знаков на растровых чертежах, и это далеко за MVP.

**3.2. Векторный слой вместо OCR.**
Раз PDF — печать из AutoCAD, координаты берутся из content stream (пути, координаты, текст с позициями), а не из `HoughCircles` и `pytesseract`. Точность на порядки выше, а код проще. OCR — аварийный путь для сканов.

**3.3. DWG — не «ещё один вход», а эталон.**
Даже если продукт нацелен на PDF (в архивах чаще всего только он), DWG по Парнасу — это **эталонный ответ**, с которым сверяется PDF-экстрактор. Без такого эталона мы не узнаем, что парсер врёт на 3 метра. Ставлю его в фундамент разработки, а не в опции.

**3.4. Две нитки, а не одна.**
На плане тепловая сеть чаще всего одна линия, а физически это подача + обратка (иногда ещё ГВС). Модель обязана уметь разворачивать одну ось в N параллельных ниток по конфигурации сети — иначе объёмы не сойдутся вдвое и IFC будет неверным. В текущем анализе этого нет вообще.

## 4. Шаги

### Ш0. Диагностика исходников · ~1 неделя

**Зачем:** узнать, что реально лежит в PDF, прежде чем проектировать экстрактор. Сейчас мы этого не знаем.

Разбираем `Раздел_РД__1_ТС_Парнас_Проект.pdf` и парный DWG: сколько страниц какого типа (план / профиль / спецификация / ведомость / общие данные); есть ли в PDF слои (OCG) и сохранились ли имена слоёв AutoCAD; чем нарисованы трассы — полилиниями или заливками; как подписаны узлы; есть ли координатная сетка и кресты; какие блоки использованы для арматуры и опор; в какой СК чертёж.

**Готово, когда:** есть отчёт-диагностика по документу и решение по каждому классу данных — «берём из вектора / берём из таблицы / просим у пользователя».

**Это самый недооценённый шаг.** Половина архитектурных решений ниже может поменяться после него.

---

### Ш1. Спецификация целевой модели · ~1 неделя

**Зачем:** зафиксировать, что именно мы генерируем, до того как что-то генерировать.

Таблица маппинга «объект сети → IFC-сущность + PredefinedType + Pset + классификация» для ТС, с заделом под ВК и ГС. Выбор единиц, структуры пространственной иерархии (`IfcProject → IfcSite → IfcFacility/IfcFacilityPart`), правил георефернса. Отдельно — набор собственных Pset для того, чего нет в стандарте: инвентарный номер, ГОСТ трубы, марка изоляции, система ОДК, тип прокладки, ссылка на страницу PDF-первоисточника.

**Готово, когда:** есть документ-маппинг и **IDS-файл** (buildingSMART Information Delivery Specification), которым выходной IFC проверяется автоматически. IDS — это наш письменный контракт с самими собой.

---

### Ш2. Нейтральная модель сети · ~1–2 недели

**Зачем:** ядро, вокруг которого всё остальное сменное.

Схема данных (JSON-схема + SQLite для проекта): узлы, участки, компоненты (арматура, опоры, компенсаторы), системы, материалы. У каждого поля — три служебных атрибута:

- **origin** — откуда взято: страница, координаты области, номер строки таблицы;
- **confidence** — насколько уверены;
- **status** — `auto` / `edited` / `confirmed`.

Без этой тройки редактор из Ш5 не построить: инженер должен видеть, откуда взялась цифра, и одним кликом попадать в нужное место чертежа.

**Готово, когда:** модель Парнаса, набитая вручную из PDF, сериализуется/десериализуется и проходит валидацию связности.

---

### Ш3. Экстракторы · ~3–4 недели

Пять независимых модулей, каждый пишет в нейтральную модель.

**3a. Геометрия из вектора.** Полилинии трасс по слоям/стилям, точки узлов, вставки блоков, тексты с позициями. Для DWG — `ezdxf`, для PDF — `pymupdf`. Один интерфейс на оба.

**3b. Калибровка листа → МСК.** Аффинное преобразование по крестам координатной сетки (2–3 точки), масштаб из штампа — как контрольная проверка, а не как источник. Если сетки нет — ручная привязка двух точек в редакторе.

**3c. Таблицы.** Спецификация по ГОСТ 21.110 и ведомость объёмов: строка → структурированная запись (Ду, толщина, ГОСТ, изоляция, Ру, Т, количество, длина). Регулярки по обозначениям + правила склейки многострочных ячеек.

**3d. Профили.** Отметки земли / верха / лотка по узлам, уклоны, длины участков, тип прокладки по пикетам.

**3e. Связыватель.** Сшивка плана, профиля и спецификации по маркам узлов (УТ-1а, ТК-2…). Здесь же — разрешение расхождений: марка есть на плане, но нет в профиле, и наоборот.

**Готово, когда:** на Парнасе из PDF извлечено ≥90 % узлов и участков, и результат совпадает с эталоном из DWG в пределах допуска из раздела 2.

---

### Ш4. Сборка топологии · ~1–2 недели

Снаппинг концов полилиний, разрезание трасс по узлам, построение связного графа, определение направления потока от источника, разворачивание оси в подачу/обратку, привязка компонентов (кран, опора) к ближайшему участку с проверкой, что это осмысленно.

Плюс правила-валидаторы: висячие концы, разрывы, участки нулевой длины, скачки диаметра без перехода, уклон вне нормы, глубина заложения вне диапазона.

**Готово, когда:** граф связен, каждая ошибка валидации — не исключение, а запись в списке задач для редактора.

---

### Ш5. Редактор · ~4–5 недель

Самая объёмная часть, и та, что определяет, будут ли инструментом пользоваться.

Три связанных вида: план поверх подложки исходного чертежа, таблица участков/узлов, профиль. Выделение синхронизировано между видами. Панель проблем — ранжированный список того, что требует решения человека: низкое доверие, конфликт источников, несходящиеся объёмы. Клик по проблеме → подсветка на чертеже и в таблице. Правки идут только в нейтральную модель, парсер при этом не перезапускается и правки не затирает.

**Готово, когда:** инженер, не читавший код, доводит Парнас до состояния «нет нерешённых проблем» за один рабочий день.

---

### Ш6. Генератор IFC · ~2 недели

Нейтральная модель → IFC 4.3 по маппингу из Ш1. Геометрия труб `IfcSweptDiskSolid` по осевой, камеры телами по габаритам, арматура и опоры в точках, системы и Pset, классификация.

**Готово, когда:** файл проходит `ifcopenshell.validate` и IDS-проверку, открывается в трёх вьюерах.

---

### Ш7. Приёмка и сверка · ~1–2 недели

Три отчёта, которые превращают «вроде похоже» в число:

1. **Геометрическая сверка** — обратный экспорт осей в DXF, наложение на исходный чертёж, карта отклонений.
2. **Сверка объёмов** — длины по Ду и типам прокладки из модели против ведомости, с расшифровкой каждого расхождения.
3. **Полнота атрибутов** — что осталось незаполненным.

**Готово, когда:** по Парнасу все три отчёта в пределах допусков из раздела 2.

---

### Ш8. Обобщение на другие сети · ~2–3 недели

Проверка главной гипотезы: другой тип сети должен добавляться **конфигурацией, а не кодом**. Словарь марок узлов, набор условных обозначений, маппинг в IFC-сущности, правила валидации — всё это данные.

Берём проект по водопроводу или канализации, пробуем пройти путь целиком, смотрим, сколько пришлось дописать в коде. Если много — возвращаемся и правим ядро; лучше узнать это на восьмом шаге, чем на двадцатом.

**Готово, когда:** второй тип сети заведён без изменений в ядре и генераторе.

## 5. Порядок и вехи

```
Ш0 диагностика ─┬─ Ш1 спецификация ──┬─ Ш2 нейтральная модель ─┬─ Ш3 экстракторы ─ Ш4 топология ─┐
                └────────────────────┘                          └─ Ш6 генератор IFC ──────────────┤
                                                                                                   ├─ Ш7 приёмка ─ Ш8 обобщение
                                                                              Ш5 редактор ─────────┘
```

- **Веха 1 (~4 нед):** ручная модель Парнаса → валидный IFC. Проверяет генератор и маппинг, до всякого парсинга.
- **Веха 2 (~9 нед):** PDF → модель → IFC без редактора, с отчётами сверки. Здесь становится ясно, чего парсер не может.
- **Веха 3 (~14 нед):** редактор, полный цикл на Парнасе за рабочий день.
- **Веха 4 (~17 нед):** второй тип сети.

Сроки — порядок величины для одного разработчика, не обязательство.

## 6. Риски

| Риск | Что делаем |
|---|---|
| В PDF не сохранились слои → трассы неотличимы от подосновы | Ш0 покажет. Запасной путь: классификация по стилю линии + ручное указание слоя в редакторе |
| Нет координатной сетки на листе | Ручная привязка двух точек; для этого редактор нужен раньше, чем по плану |
| Марки узлов на плане и в профиле не совпадают | Нечёткое сопоставление + разрешение конфликтов человеком в панели проблем |
| Подача/обратка нарисованы одной линией без указания конфигурации | Конфигурация сети задаётся в редакторе на уровне ветки, а не участка |
| Объёмы не сходятся из-за узлов и фасонины, не учтённых в ведомости | Отчёт сверки должен уметь объяснять, а не только показывать дельту |

## 7. Открытые вопросы

1. **DWG есть всегда или только по Парнасу?** Если по большинству проектов есть DWG, приоритет экстракторов меняется местами и весь Ш3a сильно проще.
2. **Кто пользователь** — вы сами, отдел, или это внешний продукт? От этого зависит, насколько всерьёз делать редактор в Ш5 (веб или десктоп, один проект или база проектов).
3. **IFC 4.3 всех устраивает?** Эталонный `ПРНС_ЛО_ТКР-ТС_У1_Э1_I2300.ifc` — IFC2X3. Если принимающая сторона умеет только 2x3, георефернс и линейные сущности придётся упрощать.
4. **В какой СК ведутся чертежи** (МСК-СПб?) и нужна ли привязка к общегородской системе.
5. **Есть ли доступ к 2–3 другим проектам** для Ш8 — и по каким типам сетей.
